## 1. Pipeline alignment / methodology

### "Why this attribution layer for each model? Did it match the retrieval pipeline?"

We attribute at LaTa L4 and PhilTa L6. Those are the anisotropy-dip layers — exactly where the paper's "ABTT recovers a collapsed middle layer" claim lives, so it is the right layer to make the *attribution* claim about. They are not the single best retrieval layers: per `runs/active/resubmit/results/perlayer_tables_v2/taskA_main.csv`, LaTa's per-layer AUCROC at L4=0.971 sits between L1=0.969 and L11=0.973, so L4 is competitive but not dominant. The honest framing is "the attribution explains the layer the paper highlights as the recovery story", not "the attribution explains the model's best retrieval head". If you push back on the layer choice, we can rerun at L11 in a follow-up; it's a few CPU-hours plus one GPU pass. [`cosine_inflation_investigation.md` §5.3]

### "Did you pool the same way as the retrieval system, or did you mean-pool while retrieval uses SIF?"

Mean-pool on the attribution side; the headline retrieval results use SIF + ABTT. That is a deliberate simplification per your earlier direction that attribution should be "ABTT only, no SIF" so the per-token mask is straightforward to reason about. The cost is a known small mismatch: the attribution-side cosine is not numerically identical to the retrieval-side cosine. The benefit is that every per-token IG / MaRC weight has a clean interpretation — "this token's contribution to the mean-pooled cosine" — without an SIF re-weighting confound. If we want full pipeline parity in v3, the retrieval pipeline already has `pool_sif` in `src/sif_abtt.py:185-210` that we can wire in. [`cosine_inflation_investigation.md` §5.4]

### "Are you applying ABTT symmetrically to both query and candidate?"

Yes, with the same `pcs` and `mean_vec` on both sides, in every variant block. The pipeline audit verified this in three places: the IG NPZ generator at `_archive/run_phase12e_pair_explanations.py:242-243, 248-266`, the metrics driver at `run_attribution_metrics.py:181-182, 200-201`, and the MaRC optimizer at `run_retrieval_mark_pair_examples.py:298-313`. Asymmetric application was one of the first hypotheses we ruled out for the cosine inflation; it is not the bug. [`attribution_pipeline_audit.md` §"Confirmed-correct items"]

## 2. Cosine fix confidence

### "How confident are you in the cosine fix? Could the same bug be hiding elsewhere?"

Quite confident on the bug itself, moderately confident there are no other instances. The bug was specific: `runs/phase12_release/pcs/<slug>/layer{L}_pcs.npz` had been built by an older phase12c pipeline that mean-pooled with a token-keep-lookup filter, then those PCs were reused by an attribution pipeline that mean-pools with no filter — two different distributions. The empirical proof is two numbers: old vs new PC1 cosine = 0.10 (essentially orthogonal) and old vs new mean_vec L2 distance = 5728 in 768-dim space. After refit, LaTa abtt full_cos drops from 0.985 to 0.564, exactly where the validation predicted. The residual concern is that the IG NPZ generator's `pool_hidden` still uses a token-keep-lookup while the metrics driver does not — that produces a small per-pair cosine difference but not the same systemic inflation. Audit finding I-1 covers this; size of the effect is < 1% on the pairs we spot-checked. [`cosine_inflation_investigation.md` §3, §5.1; `attribution_pipeline_audit.md` I-1]

### "Does the live retrieval pipeline have the same stale-PCs problem?"

No. The retrieval pipeline uses `EmbeddingCleaner` (`src/sif_abtt.py`), which fits PCs at evaluation time on the canonical train embeddings every time it's invoked — there is no stored PC bundle to go stale. The bug was specific to an offline phase12c artifact dump that the attribution pipeline reused for convenience. The new `scripts/ig/refit_pcs_for_attribution.py` we shipped this week does for the attribution side what `EmbeddingCleaner` does for retrieval: refits `mean_vec` and the top-D PCs on the same mean-pool path the attribution code actually uses, so the two stay coupled. [`cosine_inflation_investigation.md` §4.2]

### "What's the value of D, and why is it the same across models?"

D = 10 universal. That matches the per-model `abtt_optimal` decision from the 2026-03-31 meeting where we agreed D=10 was a defensible single-number-across-models choice for the resubmit pipeline. Before the cosine investigation, the attribution sampler had per-model values (LaTa 2, LaBSE 1, Qwen3-0.6B 3, PhilTa 10) which had been carried over from older `phase12f_examples.csv` bookkeeping. We harmonized to D=10 universal for the 200-positives run; that change combined with the PC refit is what makes the new abtt cosines look right. [`cosine_inflation_investigation.md` §4.1]

## 3. Story / interpretation

### "What does ρ_LOO = X actually mean for the paper claim?"

ρ_LOO is the Spearman correlation between |attribution_score(token)| and the per-token leave-one-out drop in cosine — i.e., does masking a single token change the cosine the way the attribution method said it would? The paper claim is that ABTT makes attributions faithful: post-ABTT, a token labeled "important" by IG actually moves the cosine when removed. The numbers support that for LaTa: IG ρ_LOO climbs from -0.055 (baseline) to 0.460 (abtt); DLA from 0.037 to 0.380; MaRC from -0.124 to 0.455; BERTScore from 0.206 to 0.460. Pre-ABTT the baseline cosine is dominated by anisotropic axes that any token can perturb, so per-token attributions correlate with random noise. Post-ABTT, the cosine is cleaned and per-token attributions track the actual cosine signal. [`summary.csv`: rows for `bowphs/LaTa, {ig,dla,bertscore,retrieval_mark}, {baseline,abtt}`]

### "Is MaRC pulling its weight as a method, or is IG the real story we should write up?"

IG is the real story. On LaTa, IG and MaRC tie within a couple of percentage points: ρ_LOO 0.460 vs 0.455, suff@0.25_ratio 0.735 vs 0.740. On PhilTa, MaRC actively underperforms: ρ_LOO 0.120 vs MaRC -0.120, and MaRC's compactness gets noticeably worse than IG's. Reading: IG is robust, scalar-agnostic, no per-pair optimization needed, and the attribution is a stable function of the model. MaRC is per-pair-optimized, so it inherits whatever local idiosyncrasy the optimizer finds — sometimes that's helpful, sometimes it picks up noise. We should lead the paper with IG and present MaRC as the per-pair-optimized comparison point that confirms IG isn't getting lucky on a particular kind of attribution. [`summary.csv`]

### "The 200-random told a softer story than 20-curated. Which set should we believe?"

The 200-positives. The 20-curated was selection bias — we picked illustrative pairs to make a point, so the numbers were not population estimates and the LaTeX caption of the original 20-pair table even said so. The 200-random had two confounds: (a) the cosine inflation bug, so every cell looked like ~0.95 regardless of the underlying signal, and (b) it included negatives, where the metrics are ill-defined. The 200-positives removes both confounds and is the only release-quality run; numbers in the new bundle are what we should anchor on for the paper. [`ORCHESTRA-monday-meeting-prep.md` §Context]

### "Does this experiment now support 'ABTT improves explanation quality'?"

Narrowly yes for LaTa, partially for PhilTa. For LaTa, every method we tested has higher ρ_LOO and higher Comp@25% post-ABTT, often by wide margins (IG ρ_LOO -0.055 → 0.460). For PhilTa, three of four methods improve on ρ_LOO post-ABTT (IG, DLA, BERTScore), but MaRC regresses (-0.036 → -0.120) and several gains are smaller in magnitude. The defensible framing for the paper is "ABTT improves explanation faithfulness on both models, with the strongest evidence on LaTa", and we keep this as a *supporting* plank — the headline remains the Task A and Task B retrieval improvements. We do not need this experiment to carry the paper. [`summary.csv`]

## 4. Negatives + experimental scope

### "Are negatives meaningfully gone, or did you just not look at them?"

Truly gone. The new sampler `scripts/ig/sample_positive_test_pairs.py` draws 200 *same-folder* pairs per model from the test split; no pair is a different-folder pair. We verified at the CSV level that every pair has matching `folder_id` for query and candidate, all are in the phase9 test split, and all are winnable. The justification is structural, not just empirical: Suff/Comp/Compactness all assume there is real positive cosine to localize. On a negative pair the cosine is ~0 to start, so any masking trivially preserves it (sufficiency = 1) and no masking can drop it further (comprehensiveness undefined). Including negatives was a methodological mistake in the 200-random run; pulling them out is the right fix, not a cherry-pick. [`ORCHESTRA-monday-meeting-prep.md` §Context, item 1]

### "Why does ABTT not improve metric Y on cell Z — specifically MaRC ρ_LOO on PhilTa?"

That is the one cell where ABTT actively regresses: PhilTa MaRC ρ_LOO goes from -0.036 (baseline) to -0.120 (abtt). Working hypothesis: post-ABTT, the cosine becomes more isotropic — by design — so the per-pair MaRC mask optimizer no longer has dominant axes to lock onto, and instead fits to whatever the pair's specific noise direction happens to be. IG, by contrast, integrates gradients along a path that smooths over that noise. We have not run the diagnostic to confirm this hypothesis. It is one of the open questions for a v3 design discussion; the simplest test is to compare the per-pair entropy of the MaRC mask post-ABTT vs pre-ABTT and see whether masks really are less peaked. [`summary.csv`: bowphs/PhilTa, retrieval_mark, abtt vs baseline]

## 5. Audit followups

### "What still needs to be fixed before we submit, given the audit?"

Four critical items, all documentation rather than numerical re-runs. First, the auto-generated LaTeX caption still claims "80 hand-selected pairs … 20 per model" — it has to be updated to match the actual run (200 random in the v2 table, 200 positives in the v3 table). Second, the LOO noise-floor caption says |Δ| < 10⁻⁴ but the code constant `LOO_NOISE_FLOOR` is 10⁻⁶; two orders of magnitude, easy reviewer catch. Third, "Compactness" is mis-attributed to MaRC (Brinner & Zarrieß 2023) — the metric we actually compute is the minimum-rationale-fraction-to-recover-80%-cosine, which is closer to Bastings et al. 2019 / DeYoung et al. 2020. Either rename it to "MinFrac@0.8" or implement the actual MaRC contiguity term. Fourth, the random-baseline RNG is reseeded per pair (`np.random.default_rng(0)` inside the loop), so the std reported for the random row is too narrow — means are unbiased because the uniform distribution is symmetric, but any std-based comparison with the random row is overstated. None of these block the meeting; they block submission. [`attribution_pipeline_audit.md` C-1, C-2, C-3, C-4]

## 6. Forward-looking

### "What would you change for a v3 experiment if we had more time?"

In priority order: (1) reconcile the token-keep-lookup pooling between the IG NPZ generator and the metrics driver — right now the IG decision scalar is pooled with a filter while the metrics driver is not, so `full_cos` in the table is a slightly different number than the cosine IG was attributing to. Fix is mechanical, not conceptual. (2) Add a SIF-pooled variant of attribution so we can claim full pipeline parity with the retrieval head, not just structural similarity; the SIF code already exists in `src/sif_abtt.py`. (3) Fix the random-baseline RNG so the std is meaningful and we can report a proper "method X beats random by Y σ" claim. (4) Add a third model to the table; Qwen3-0.6B is in the sampler config but not in the 200-positives run because we scoped Run 2 to LaTa and PhilTa for time. None of these would change the headline finding; they would all tighten the audit-readiness of the table. [`attribution_pipeline_audit.md` I-1, §5.4 of cosine investigation]

### "If the cosine inflation could happen here without you noticing for weeks, what's your process change so it doesn't happen again?"

Two changes already in this branch. First, `refit_pcs_for_attribution.py` now refits the PC bundle from the same mean-pool path the metrics code actually uses, so the PCs and the embeddings are bound by construction — there is no decoupled artifact to go stale. Second, the audit doc enumerates 20+ confirmed-correct items alongside the bugs; that template now exists for any future pre-meeting numerical sweep. Process gap that remains: we did not have an automated sanity check on `full_cos` ranges in the metrics driver — a 0.95 floor across baseline AND abtt AND every method should have triggered an assertion. Easy add for v3: assert that the abtt full_cos distribution is statistically distinct from the baseline distribution before allowing a `summary.csv` to be written.
